# Core framework completion

The complete Core launcher also needs a usable external module contract. This change closes the two Core gaps identified in [product-spec section 17](../product/product-spec.md#17-core-framework-and-remaining-acceptance): applying saved module-instance configuration at runtime and validating packaged discovery descriptors. It adds a separately consumable SDK and a [standalone add-on](../../examples/standalone-sort-addon/README.md) to prove that the public boundary does not depend on the Core project or signer.

## Acceptance matrix

| Requirement | Implementation and review target | Evidence to record |
| --- | --- | --- |
| Offline Core-only launcher remains complete | Built-in Home, alphabetical list, exact activity/profile launch, search, gear, themes, Settings, and recovery remain in Core. Optional providers must not block first render. | Existing Home, navigation, appearance, catalog, and search tests; physical checks below. |
| Instance identity and configuration reach the provider | The selected context binding supplies its stable Core instance ID and JSON to protocol-v4 `getInstanceCapabilityBinder`. The SDK returns an endpoint tied to a normalized configuration snapshot; changing configuration revokes the old endpoint. Protocol-v1–v3 providers accept only `{}` configuration. | `InstanceConfigurationPolicyTest`, `HomeSortControllerTest`, and the cross-APK two-instance sort smoke test. |
| Configuration is bounded and validated | Core and SDK share `ModuleDescriptorCodec`: descriptor ≤32 KiB; configuration ≤8 KiB; flat schema ≤32 fields; unknown keys or invalid types/values fail. Missing fields receive defaults. An invalid edit keeps the saved configuration; Home falls back to Core alphabetical order if an invocation fails. | `ModuleDescriptorCodecTest`, composition/management tests, cross-APK invalid configuration checks. |
| Independently configured instances behave independently | The reference provider uses `reverse` from its per-instance context. Two instances of that one provider, bound in separate contexts, produce forward and reverse order; switching back restores the first. Core remaps returned keys to current catalog objects. | `AppSortCrossApkSmokeTest` and sort controller tests. |
| Stale results cannot override active Home | Context/configuration/catalog changes, provider disable/removal, timeouts, and invalid sort permutations leave or restore Core ordering. Old instance endpoints lose authority when replaced or their session ends. | Sort controller, result validator, registry lifecycle, and cross-APK smoke tests. |
| Discovery descriptors are validated | Core reads a raw JSON resource named by service metadata, parses the bounded v1 descriptor, compares its identity, protocol range, capabilities, Core requests, and full runtime descriptor with the Binder handshake, and records incompatibility without granting authority from metadata. | Descriptor parser tests, registry descriptor/incompatibility tests, cross-APK discovery. |
| Existing wire compatibility and security survive | Root AIDL transactions 1–8 remain intact; v4 adds descriptor query at 9 and per-instance acquisition at 10. Capability major versions stay explicit. Core grants remain tied to package plus current signer and checked live; SDK capability Stubs verify Core callers. | Existing security and registry tests plus v4 cross-APK smoke. |
| Public development path works | Maven-layout `module-api:0.2.0` and `module-sdk:0.2.0` AARs are published as the SDK artifact. The standalone example builds with an external repository path and no Core source/project dependency or Core signing key. | Run the independent example Gradle build against the published repository artifact. |
| Management and recovery remain usable | Enable/disable, retry, 200-entry local event history, instance/context editing, atomic activation, live grant revocation, and Android uninstall handoff retain saved unresolved references and reachable Home/Settings. | Existing management, composition, security, and UI tests; device uninstall check below. |

The [add-on development guide](../addon-development.md) documents the exact descriptor, SDK hooks, version rules, and caller trust requirements. The official reference APK demonstrates an optional helper; the standalone example demonstrates a different signing identity and published-artifact consumption. A signed APK is still needed for runtime testing against the owner's persistently signed Core build; disposable CI debug certificates do not match the example's published pins.

## Validation status and physical-device acceptance

Record the commit-specific Android CI build, unit/lint, emulator IPC, and independent SDK-example build results for this change. Source review or successful compilation does not establish device behavior. The [Core completion](core-completion.md#physical-device-acceptance) device checklist still requires HOME role selection, actual launches, long keyboard queries and insets, TalkBack focus, compact/large-font layouts in all themes, work-profile transitions, process death, OEM package updates, and Android uninstall cancellation and success. Keep these device results separate from automated CI evidence.

## Later work

This contract provides bounded flat configuration fields and a JSON editor. Rich schema-driven forms and configuration UX, external Home/Drawer surfaces, external theme loading, filter providers, richer installation/distribution, automation, scripts, MCP transport, and terminal providers remain later roadmap phases. None is needed for a Core-only launcher or the per-instance sort proof.
